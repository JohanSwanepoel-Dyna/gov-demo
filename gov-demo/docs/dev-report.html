Issues

1

No spans from the Python services

Dynatrace dataTelemetryFixed30 Oct
What happened
Traces showed only web and legacy-stub. claims-api, payment-worker and llm-gateway were missing.
What the data showed
DQL: logs from all 8 workloads reached the tenant but spans came only from the Node and Java services. In the claims-api pod the agent was preloaded but created no Python runtime.
Cause
Likely: the OneAgent FastAPI, Starlette and psycopg2 sensors are off in the tenant and the app uses psycopg 3. Not confirmed.
Fix and proof
OpenTelemetry for the Python services alongside OneAgent for Node and Java, through the in-cluster telemetry-ingest collector.
2

Wrong parent on the legacy-stub span

Dynatrace dataTelemetryFixed30 Oct
What happened
The Java span hung under the web client span instead of the calling service, and web timestamps ran about 120 ms late.
What the data showed
590 of 590 queue rows carried a single Dynatrace entry in tracestate (@dt=fw4;...).
Cause
OneAgent on the Java side read the Dynatrace tracestate entry that the OpenTelemetry services passed through unchanged (hypothesis, verified by the fix).
Fix and proof
A propagator in the three Python services drops tracestate entries ending in @dt. Verified: POST /legacy/CustomerService is parented to the claims-api client span, POST /legacy/PaymentService to the payment-worker client span.
3

RUM saw one view, so no funnel was possible

Dynatrace dataWeb experienceFixed30 Oct
What happened
455 events and 17 sessions arrived, every session with a single view and no step actions.
What the data showed
Checked user.events after building the Playwright load. Funnel after the fix: 12, 12, 12, 12, 8, 5, 5 sessions per step.
Cause
The single page app used hash routes, which RUM does not treat as views. A try/catch also hid a bug: leaveAction was called on the wrong object.
Fix and proof
History API routing with real paths and an Express fallback for the seven step URLs, and a corrected enterAction/leaveAction call.
4

Vulnerabilities were never flagged

Dynatrace dataSecurityFixed11 Nov
What happened
The old Log4j in legacy-stub did not appear in Security, although it was confirmed loaded in the JVM (423 classes).
What the data showed
No vulnerability events at all in 7 days, only compliance events. The runtime vulnerability setting had no object, so defaults applied.
Cause
Runtime vulnerability analytics is off by default in a tenant.
Fix and proof
Two scoped settings objects that monitor only the gov-demo namespace. Verified: 102 distinct vulnerabilities in 24 hours in one namespace, log4j-core 2.14.1 flagged CRITICAL. First findings took longer than 12 minutes.
5

Every proxied call was named POST /

Dynatrace dataTelemetryFixed11 Nov
What happened
In Dynatrace the web service showed one route for all API traffic, which hid which endpoint was slow.
What the data showed
Route breakdown for web: POST / dominated with p95 about 1 s, while the real endpoints were invisible.
Cause
The proxy was mounted with app.use and no path, so Express reported the route as /.
Fix and proof
One Express route per API endpoint plus a fallback. Verified: 159 of 160 spans on the new pod carry the route, for example POST /api/claims/:claimId/eligibility at p95 157 ms and POST /api/assistant at p95 1,585 ms.

7

Requests to unmonitored hosts in the service map

User in the UITopologyAccepted30 Oct

What the data showed

8

Locust stopped creating claims

User in the UILoadFixed2 Nov
What happened
make up showed no data. The tenant had no business events for 30 minutes.
What the data showed
Locust counters: POST /api/assistant 46,305 against POST /api/claims 2,890. Postgres held 0 claims after retention ran.
Cause
Switching to the assistant profile and back left Locust with the restricted user classes, so all four users were chat users.
Fix and proof
Two attempts. Draining users on a profile change did not help. Naming the classes explicitly for every profile did: claims created went from 18 to 53 in the retest.
9

Masking missed digits and risked trace ids

Hands-on testPrivacyFixed30 Oct
What happened
A first pattern for TFN and Medicare numbers looked fine on paper.
What the data showed
Read-only DQL on real data: a bare nine-digit pattern hit digits inside the hex trace_id and left the last digit of a ten-digit Medicare number.
Cause
No label anchor in the pattern.
Fix and proof
Patterns anchored on the label with a lookbehind. Verified: 6 of 6 log lines and 28 of 28 prompt spans masked, none in clear. 373 older prompts recorded before masking stayed in clear until retention.
10

The legacy stub killed its own demo

Hands-on testResilienceFixed30 Oct
What happened
In slow mode the pod restarted partway through the peak and the toggle reset to normal.
What the data showed
Found by running monday_peak. A reset during the peak could not reach the stub either.
Cause
The health probe shared the 8 Tomcat threads, so liveness failed under load. The control API starved the same way.
Fix and proof
A separate HTTP server on port 8301 for health and control. Under saturation the main port timed out after 8 s while 8301 answered in 0.02 s.

12

The submission SLOs never burned

Hands-on testSLOsFixed30 Oct
What happened
During monday_peak the submission availability and latency SLOs stayed at 100 percent.
What the data showed
Every indicator was run as a query against the peak data before creating it.

13

A dashboard tile reported the wrong thing

Hands-on testDashboardsFixed30 Oct
What happened
Where sessions end showed stale and misplaced sessions.
What the data showed
Checked the values, not only that the query ran: it counted 20 single-view sessions from the hash routing era and placed completers wrongly because view events are not strictly ordered.
Cause
It used the last view per session.
Fix and proof
Replaced by furthest step reached per session. Final numbers agree with 5 of 14 sessions completing.
14

OpenPipeline and query gotchas

Hands-on testPipelinesFixed30 Oct
What happened
The tenant rejected the first pipeline apply, and some queries returned nothing.
What the data showed
contains() is not enabled in OpenPipeline matchers. dtctl apply --dry-run is not server-side validation. matchesPhrase returns nothing on JSON log text in a fetch. OneAgent log ingestion lifts only trace_id and span_id.
Cause
Platform behaviour that is not obvious from the documentation.
Fix and proof
matchesPhrase in matchers, contains() in fetch queries, JSON parsed first in the pipeline. All recorded in the runbook.

17

dtctl lost its login when calls ran in parallel

Hands-on testProcessFixed30 Oct, 11 Nov
What happened
dtctl asked for a new login. It happened twice, including during this session.
What the data showed
invalid_grant: the refresh token was reused. Several dtctl processes had refreshed the OAuth token at the same moment.
Cause
Parallel dtctl calls, including a background poller next to a foreground query.
Fix and proof
Rule: one dtctl call at a time, no parallel monitors. The user logs in again.
